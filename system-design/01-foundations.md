## 1. CAP 定理

### 是什么
CAP 定理由 Brewer 提出，后被 Gilbert 和 Lynch 证明：在一个分布式数据系统中，当网络分区（Network Partition，P）不可避免地发生时，你无法同时在所有时刻保证强一致性（Consistency，C）和高可用性（Availability，A）。也就是说，分布式系统的三要素 C、A、P 里，P 是现实中必然存在的（网络一定会断），真正要选的是「断网时保 C 还是保 A」。

### 关键点（可背）
- C：一致性——所有节点在同一时刻看到完全相同的数据（读到的一定是最新写入）。
- A：可用性——每一个请求都能在合理时间内收到非错误的响应（不保证是最新数据）。
- P：分区容忍——网络分片后系统仍能继续运转。
- 三选二是流行但不严谨的说法；准确表述是「因为 P 必须接受，所以在 P 发生时在 C 和 A 之间做取舍」。
- 常见归类：CP 系统（ZooKeeper、etcd、HBase）——宁可拒绝服务也要一致；AP 系统（Cassandra、DynamoDB、DNS）——宁可返回旧数据也要可用。
- 工程上多数互联网业务选 AP + 最终一致性，因为完全不可用的损失通常大于短暂读到旧数据。

### 面试怎么答
「CAP 讨论的是网络分区发生时的取舍。正常网络下 C 和 A 可以同时满足；一旦出现分区，CP 系统会拒绝部分请求以保证不读到不一致数据，AP 系统继续对外服务但可能返回旧值。我们做业务系统时，绝大部分读多写少场景选 AP 加最终一致性，因为用户刷不到最新一条动态的体验远好于整个页面打不开；但像账户余额、库存扣减这类不能错的场景，宁可牺牲可用性也要 CP。」

### 常见追问
- 最终一致性和强一致性怎么选？——看业务错了能不能容忍：余额不能容忍选强一致，Feed 流可以容忍秒级延迟选最终一致。
- 有没有系统同时是 CA？——单节点数据库可以近似 CA，但一旦分布式、有副本就面临 P。
- 分布式事务怎么和 CAP 配合？——BASE 理论 Basically Available、Soft state、Eventually consistent 就是 AP 思路的落地。

## 2. 一致性模型

### 是什么
一致性模型描述的是「一个写入成功之后，后续的读操作能看到什么」。从最严到最松大致是：线性一致性（强一致）、顺序一致性、因果一致性、读己之写、单调读、最终一致性。理解一致性模型是设计存储和缓存组合的前提。

### 关键点（可背）
- 线性一致性（Linearizable）：全局像只有一个副本，任何读都一定读到最新写入，相当于串行执行，代价最高。
- 顺序一致性：所有节点看到的操作顺序一致，但不保证和实时时间一致。
- 因果一致性：有因果关系的操作顺序被遵守，无因果的可以乱序。
- 读己之写：用户自己写完一定能读到，别人不保证。
- 单调读：一个用户读到某值后，后续不会读到更旧的值。
- 最终一致性：允许短暂不一致，但保证没有新写入后，所有副本最终收敛到相同值。
- 工程实践：缓存 + DB 场景常用「先更新库、再删缓存」或「延迟双删」来逼近读己之写。

### 面试怎么答
「一致性模型是个谱系不是开关。最强的是线性一致，适合钱和库存；最常见的是最终一致，适合内容和社交。我在做缓存时会区分：用户自己的操作（发帖、下单）用读己之写，关键路径上加一次缓存失效或读穿透；跨用户的读（刷 Feed）容忍最终一致。选模型的本质是拿一致性换性能和可用性。」

### 常见追问
- 先删缓存还是先更新数据库？——普遍推荐先更新库再删缓存；删除失败用消息队列重试，极端情况加延迟双删。
- 缓存和数据库不一致怎么办？——给缓存设短 TTL + 删缓存重试队列 + 订阅 binlog 做兜底。
- 什么是快照隔离、可重复读？——那是单库事务隔离级别，和分布式一致性模型是两套概念，别混。

## 3. 可用性、可靠性与扩展性

### 是什么
这三个词经常被混用，但面试里必须分清。可用性（Availability）= 系统正常对外服务的时间比例，常说几个 9；可靠性（Reliability）= 系统在给定时间内不出故障的概率；扩展性（Scalability）= 加机器能不能线性提升吞吐。三者共同构成「非功能性需求」的骨架。

### 关键点（可背）
- 可用性 SLA：两个 9=99%（年宕机 ~3.65 天），三个 9=99.9%（~8.76 小时），四个 9=99.99%（~52 分钟），五个 9=99.999%（~5 分钟）。
- 高可用手段：多机房多活、冗余副本、无状态服务、熔断降级、限流、超时与重试、灰度发布。
- 可靠性手段：幂等设计、持久化 WAL、副本同步、对账、故障自动转移。
- 扩展性分两类：垂直扩展（纵向，单机加 CPU/内存，有上限）和水平扩展（横向，加机器，靠分片）。
- 扩展的前提是无状态——状态尽量外移到 Redis / DB，让应用节点可以随便加随便删。

### 面试怎么答
「我会先问业务要几个 9。一般内部系统三个 9 够了，面向 C 端的支付和登录要四个 9 以上。达到高可用靠的不是单点做得多稳，而是『出故障是必然』的假设下做冗余：无状态应用多副本跨可用区，数据库主从+自动切换，再加熔断限流兜底。扩展性的关键是把状态从进程里挪出去，这样加机器就是加一个无差别节点。」

### 常见追问
- 怎么算系统容量？——看峰值 QPS 和单机承载，反推需要多少节点，再留 50% 冗余。
- 多活和主从区别？——主从只有一个主写、从做灾备；多活多个机房都能写，代价是跨机房一致性很难。
- 降级和熔断区别？——熔断是下游挂了快速失败别把线程池打满；降级是主动关掉非核心功能保核心链路。

## 4. 负载均衡

### 是什么
负载均衡（Load Balancer）把大量请求分发到一组后端实例上，避免单机被打挂，同时让用户就近访问。它可以是硬件（F5）、软件（Nginx、HAProxy）、四层（LVS，按 IP+端口转发）或七层（Nginx/Envoy，按 URL、Header、Cookie 路由）。在微服务时代又派生出客户端负载均衡（客户端自己选节点，如 Ribbon/Spring Cloud LoadBalancer）和服务网格（Sidecar，如 Envoy/Istio）。

### 关键点（可背）
- 常见算法：轮询、加权轮询、最小连接数、一致性哈希（有状态会话/缓存场景）、随机。
- 四层 vs 七层：四层基于 IP+端口转发，性能高但不看内容；七层能按 URL/Header 路由，灵活但要解析报文。
- 全局负载均衡 GSLB：在 DNS 层把不同地域用户导到最近机房。
- 健康检查：LB 要主动探测后端，挂掉的节点自动摘除。
- 会话保持：无状态服务不需要 sticky session；必须保持时用一致性哈希或会话集中存 Redis。

### 面试怎么答
「我们一般分两层：入口用七层 LB（Nginx/云 LB）做 HTTPS 终结和按路径路由，服务间用客户端负载均衡 + 服务发现，节点列表从注册中心拉。算法默认加权轮询，对有长连接或本地缓存的服务用一致性哈希，让同一个请求尽量落到同一台机器，提高缓存命中率。所有后端都挂健康检查，超时两次就摘流，恢复后自动加回来。」

### 常见追问
- 一致性哈希解决什么？——节点增减时只迁移少量 key，避免哈希取模导致的全量重映射。
- LB 自己会不会单点？——会，所以 LB 通常双机热备或用云厂商多可用区部署。
- 会话粘滞好还是不好？——不好，破坏无状态扩展性，能用 Redis 共享会话就别粘滞。

## 5. 缓存策略

### 是什么
缓存用空间换时间，把热点数据放在离计算最近的地方（浏览器/CDN/本地内存/Redis），减少对后端数据库的读压力。缓存是提升读性能最便宜的手段，但也是一致性问题的重灾区。面试必考缓存位置、缓存模式、缓存失效策略和三大经典问题（穿透/击穿/雪崩）。

### 关键点（可背）
- 缓存位置层级：浏览器缓存 → CDN → 网关/反代缓存 → 应用本地缓存（Caffeine/Guava）→ 分布式缓存（Redis）→ 数据库。
- 读写模式：Cache-Aside（应用先查缓存，miss 再查库回填）最常用；Read-Through / Write-Through 由缓存层代理写库；Write-Behind 异步回写（高性能但有丢数据风险）。
- 失效策略：过期时间 TTL、主动失效（删 key）、LRU/LFU 淘汰。
- 穿透：查不存在的数据，绕过缓存直击 DB。解决：布隆过滤器拦不存在的 key + 空值缓存。
- 击穿：某个热点 key 过期瞬间，大量请求同时打 DB。解决：互斥锁（setnx 单线程回填）+ 热点 key 永不过期。
- 雪崩：大量 key 同时过期或缓存集群宕机。解决：TTL 加随机抖动、多级缓存、缓存高可用、限流兜底。

### 面试怎么答
「读路径我用 Cache-Aside：先读 Redis，命中直接返回；未命中读数据库，再异步写回 Redis 并设 TTL。为了防穿透，对空结果也缓存短 TTL，并在前面加布隆过滤器挡住肯定不存在的请求。为了防击穿，热点 key 不设物理过期，而是后台异步刷新，或者只允许一个请求去回填、其他等待。为了防雪崩，TTL 全部加随机抖动，避免同一时刻大面积失效。写路径是先更数据库再删缓存，删失败进消息队列重试。」

### 常见追问
- Redis 为什么快？——纯内存、单线程避免锁竞争、IO 多路复用、高效数据结构。
- 缓存和 DB 双写一致性？——短时间不一致可接受就最终一致；要强一致就别走缓存或加分布式锁。
- 本地缓存和 Redis 怎么配合？——一级本地缓存扛超热点，二级 Redis 扛大部分，DB 兜底；本地缓存用短 TTL 控制不一致窗口。

## 6. 消息队列

### 是什么
消息队列（Message Queue）在两个服务之间插入一个异步缓冲层，把同步调用改成「生产者发完就走，消费者按自己节奏处理」。它解耦了上下游、削平了流量峰值、还提供了异步执行能力。常见产品有 RabbitMQ、RocketMQ、Kafka、Pulsar。面试重点是选型、消费模型、顺序性、重复消费和积压处理。

### 关键点（可背）
- 三大作用：解耦（上下游不互相依赖）、异步（把非主流程拆出去）、削峰（突发流量先堆在队列里慢慢消费）。
- 选型：Kafka 高吞吐日志/大数据管道；RocketMQ 事务消息/顺序消息/电商业务；RabbitMQ 路由灵活、延迟队列好用。
- 消费模型：点对点（一条消息一个消费者）和发布订阅（广播给多个 consumer group）。
- 至少一次（At-least-once）投递是主流，意味着可能重复，所以消费端必须幂等。
- 顺序消息：同一业务 key 发到同一队列/分区，单线程消费。
- 积压处理：临时扩容消费者 + 跳过非关键消息 + 紧急批量转发到新 topic。

### 面试怎么答
「MQ 在我这儿首先是削峰和解耦工具。秒杀场景下单请求先落库再发消息，库存和订单服务按自己能力消费，哪怕瞬时 10 万 QPS 也不会把数据库打死。我选 Kafka 做日志和埋点管道，选 RocketMQ 做业务消息因为它支持事务消息。重复消费我不依赖 MQ  exactly-once，而是在消费端用业务唯一 ID 做幂等表。顺序性靠按用户 ID 哈希路由到固定队列保证。」

### 常见追问
- 消息丢了怎么办？——生产者确认+Broker 持久化+副本+消费端手动 ack，四段都要开。
- 事务消息知道吗？——RocketMQ 的半消息机制：先发半消息到 MQ（对消费者不可见），本地事务成功再提交，失败回滚，解决本地事务和发消息的原子性。
- 怎么保证消息不重复？——业务幂等：唯一索引、状态机、去重表。

## 7. 数据库选型：SQL vs NoSQL

### 是什么
数据库选型是系统设计的分水岭题。SQL（MySQL/PostgreSQL）强调事务、结构化、强一致；NoSQL 又细分键值（Redis/DynamoDB）、文档（MongoDB）、宽列（HBase/Cassandra）、图（Neo4j）、时序（InfluxDB）。没有银弹，按数据模型、访问模式、一致性需求和规模来选。

### 关键点（可背）
- 什么时候选 MySQL：事务强、结构稳定、关系复杂、需要二级索引和 join。
- 什么时候选 Redis：纯内存、极快、做缓存/会话/排行榜/分布式锁/计数器。
- 什么时候选 MongoDB：JSON 文档、schema 灵活、迭代快、内容类业务。
- 什么时候选 HBase/Cassandra：超大规模写、宽表、按 rowkey 顺序读写、能容忍弱一致。
- 什么时候选 ES：全文检索、模糊搜索、聚合分析。
- 什么时候选图数据库：社交关系、风控链路、多层好友推荐。
- 分库分表是单表到亿级后的必经之路，但要付出跨分片事务和查询复杂化的代价，能靠业务拆就别过早分。

### 面试怎么答
「我默认用 MySQL 做主存储，因为交易和数据正确性最重要。读多的热点数据前面加 Redis 缓存。搜索和模糊匹配单独抽 ES，不要在 MySQL 里 like '%xx%'。日志和埋点走 Kafka 进 ES 或 ClickHouse。如果遇到 schema 快速变化的内容业务，用 MongoDB。选型原则是：先想清楚访问模式是点查还是范围查、要不要事务、数据量多大，而不是追时髦。」

### 常见追问
- 为什么不用 NoSQL 替代 MySQL？——NoSQL 牺牲事务和 join 换扩展性，财务系统不能这么干。
- 分库分表怎么做？——按用户 ID 哈希分表，用雪花 ID 保证全局唯一，非分片键查询用冗余索引表或 ES 兜底。
- MySQL 单机扛多少？——经验值：简单点读 QPS 几千到一万，复杂查询几百；写 TPS 看行锁竞争，一般几千。

## 8. 分布式 ID 生成

### 是什么
分库分表后不能再用单表自增主键，需要一个全局唯一、趋势递增、高性能的 ID 生成方案。常见方案有 UUID、数据库号段、雪花算法（Snowflake）、Redis INCR、号段模式（Leaf）、美团/滴滴的优化版。面试重点是各方案优缺点和时钟回拨问题。

### 关键点（可背）
- UUID：简单但太长（128bit）、无序、做主键索引插入性能差。
- 数据库自增：简单但单点、扩展瓶颈。
- 号段模式：一次拿一段 ID（如 1-1000）放在内存里慢慢用，用完再取下一段，DB 压力小、可容灾。
- 雪花算法 Snowflake：64bit = 1 符号位 + 41 时间戳 + 10 机器位 + 12 序列号，本地生成无需 network、趋势递增。
- 雪花痛点：时钟回拨——机器时钟被 NTP 往回调可能发重复 ID；解决是回拨小就等待，回拨大就报错切备用机器。
- 趋势递增的意义：InnoDB 主键聚簇索引，顺序插入比随机插入快很多。

### 面试怎么答
「分库分表后我用号段模式或雪花。号段模式优点是简单可靠，DB 里维护一张 max_id 表，业务方一次领 1000 个在内存分配；缺点是有中心化。雪花算法是本地生成，每个实例配唯一 workerId，64 位里塞时间戳、机器号、序列号，趋势递增对索引友好。我会专门处理时钟回拨：回拨超过阈值就拒绝发号并告警，小于阈值就sleep等待追上来。」

### 常见追问
- 为什么不直接用 UUID？——无序导致 B+ 树页分裂，写放大严重。
- 号段模式挂了怎么办？——业务内存里还有一段够用，多个号段服务多实例部署互相备份。
- 一秒钟能发多少 ID？——雪花单节点 4096/毫秒 = 409.6 万/秒，够用。

## 9. 微服务 vs 单体

### 是什么
单体（Monolith）是把所有功能打包成一个进程部署；微服务（Microservices）把系统按业务域拆成多个独立服务，各自开发、部署、扩缩容。没有绝对好坏，关键看团队规模和业务复杂度。

### 关键点（可背）
- 单体优点：开发调试简单、部署一个包、分布式问题少。缺点：代码库膨胀、牵一发动全身、技术栈绑死、扩缩容只能整体扩。
- 微服务优点：独立部署、独立扩展、技术栈自由、故障隔离。缺点：分布式复杂度（网络、一致性、运维）、服务间调用链长、测试难。
- 拆分时机：团队超过 2 个、不同模块扩展需求差异大、发布互相阻塞时再拆。
- 拆分依据：按业务领域（DDD 限界上下文）拆，不要按技术层拆。
- 配套设施：服务注册发现、配置中心、网关、链路追踪、熔断限流、CI/CD。

### 面试怎么答
「我不迷信微服务。新项目、小团队先单体，用模块化代码把边界划清楚，等业务验证、团队长起来再按业务域拆。拆的时候先拆变化最频繁、扩展需求最不一样的模块（比如交易和推荐），不要一上来就拆几十上百个。微服务的真正成本不在拆，而在拆完之后的注册发现、链路追踪、故障隔离这些基建，没这些基建拆了就是灾难。」

### 常见追问
- 微服务之间怎么通信？——同步用 HTTP/gRPC，异步用 MQ；能异步就别同步。
- 分布式事务怎么处理？——尽量避免跨服务强事务，用最终一致 + 本地消息表/事务消息 + 对账兜底。
- 服务拆分粒度？——一个服务能由一个小团队两周内重新写出来就差不多。

## 10. 幂等与重试

### 是什么
网络会超时、服务会重启，所以任何一次写请求都可能被重试多次。幂等（Idempotency）指同一个请求执行一次和执行 N 次效果相同。重试是把短暂失败再试一次的手段，但如果接口不幂等，重试就会造成重复下单、重复扣款。

### 关键点（可背）
- 天然幂等：读操作、按主键删除、设置固定值（set x = 5）。
- 不幂等：创建订单（insert）、扣库存（decr by 1）、转账。
- 实现手段：客户端带唯一请求号（requestId），服务端先查请求表，已处理直接返回结果；数据库唯一索引兜底；状态机限制只能从待支付到支付成功一次。
- 重试策略：立即重试只适合网络闪断；指数退避 + 抖动更稳妥；设最大次数避免无限重试。
- 重试和超时要配合：上游超时时间要大于下游 P99 响应时间，否则会疯狂重试。
- 幂等键放哪：写在 Header（Idempotency-Key）或业务字段里，不要依赖传输层。

### 面试怎么答
「我对所有写接口默认做幂等。客户端生成一个全局唯一的 requestId 放在 Header，服务端用这个 ID 落一张去重表：第一次请求正常处理，结果也存下来；超时重试时先查去重表，有结果直接返回，没结果才继续。扣库存这类用数据库唯一约束或乐观锁版本号兜底。重试我用指数退避，最多 3 次，并且配合熔断——下游已经挂了就别再重试凑热闹。」

### 常见追问
- 去重表要保留多久？——至少超过业务最大超时窗口（比如 24 小时），定期归档。
- 幂等表本身写不进去怎么办？——那就是真系统故障了，让上游快速失败，别假装成功。
- 怎么设计一个安全的支付回调？——回调是第三方重试的，必须用订单号做唯一键，回调逻辑幂等。

## 11. 限流

### 是什么
限流（Rate Limiting）在系统入口按时间窗口限制请求数量，超过就拒绝或排队，保护后端不被流量压垮。它是高可用最后一道防线。常见算法有固定窗口、滑动窗口、漏桶、令牌桶。

### 关键点（可背）
- 固定窗口计数：简单，但窗口边界会有 2 倍突刺（比如 59 秒和 01 秒各打满）。
- 滑动窗口：把大窗口切成小格滑动统计，解决边界突刺。
- 漏桶（Leaky Bucket）：请求以任意速率进来，以固定速率漏出，平滑流量；不适合允许突发的场景。
- 令牌桶（Token Bucket）：按固定速率往桶里放令牌，请求拿到令牌才通过，桶满了允许一定突发；Guava RateLimiter 和 Sentinel 默认就是令牌桶思路。
- 分布式限流：单机算法不够，用 Redis + Lua 做全局限流，或网关层统一拦。
- 限流维度：按用户、按 IP、按接口、按租户；要给返回明确的 429 或 Retry-After。

### 面试怎么答
「我一般在网关层做全局限流，算法选令牌桶，因为它既能控平均速率又允许合理突发。维度上按用户 ID 限流（防单个用户刷爆），再按接口维度兜底（比如登录接口单独限流防暴力破解）。实现用 Redis 存计数 + Lua 保证原子。被限流的请求返回 429 并带 Retry-After 头，前端做友好提示。服务内部再加 Sentinel 做熔断和线程池隔离，防止某个慢接口拖垮整个进程。」

### 常见追问
- 限流和熔断区别？——限流是控制进来的量；熔断是发现下游挂了直接断开调用，防止级联故障。
- 漏桶和令牌桶怎么选？——要绝对平滑输出用漏桶（比如调下游支付）；允许突发用令牌桶（正常用户访问）。
- 分布式限流怎么保证准？——Redis 单线程 + Lua 原子操作即可，允许极小误差。
