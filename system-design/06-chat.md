# 06 · 案例：聊天系统（即时通讯）

> 考察重点：长连接、在线状态、消息不丢不重不丢序、推拉结合。

---

## 一、需求

**功能需求**
- 单聊：A 给 B 发消息，B 实时收到。
- 群聊：一群人收发消息。
- 消息已读、未读数、离线消息拉取。
- 支持图片、文件（不要求音视频）。

**非功能需求**
- 消息端到端延迟 < 300ms。
- 消息不能丢、不能重、不能乱序（同一会话内）。
- 同时在线长连接百万级。
- 离线用户上线后能补齐离线期间的消息。

---

## 二、规模估算

- DAU 1 亿，同时在线 1000 万。
- 人均每天发 20 条消息，读 100 条 → 写 QPS ≈ 1亿×20/86400 ≈ 2300，读 QPS ≈ 1.1 万。
- 峰值写 5 倍 ≈ 1.2 万 QPS。
- 单条消息平均 500 字节（含元数据）。
- 日消息总量 20 亿条，存储 ≈ 1TB/天。

---

## 三、高层设计

```
   Client (App/Web)
       │  WebSocket / 长连接
       ↓
┌─────────────┐
│  接入层 (LB) │  按用户 ID 一致性哈希把连接固定到某台网关机
└──────┬──────┘
       ↓
┌─────────────┐     ┌──────────────┐
│  网关集群    │────→│ 会话/路由服务  │  记录 userId → 网关机 映射
└──────┬──────┘     └──────┬───────┘
       ↓                    ↓
   ┌─────────┐        ┌──────────┐
   │  消息路由 │        │ Redis 在线表│
   └────┬────┘        └──────────┘
        ↓
  收件人在线吗？
   ├─ 在线：推到收件人所在网关机 → WebSocket 下发
   └─ 离线：写离线消息存储（MongoDB/Cassandra），等上线拉
        ↓
  持久化：所有消息写 DB（按会话分片）
```

---

## 四、核心组件细节

### 4.1 长连接接入
- 客户端和接入网关之间用 WebSocket（或自建 TCP 协议）。
- 接入层无状态但连接有状态：用一致性哈希把同一个用户固定到同一台网关机，避免重复建连。
- 网关机维护一张 `userId → connection` 内存表。
- 心跳 30 秒一次，连续两次心跳断就判定下线。

### 4.2 消息路由
- A 发消息给 B：A 的网关机收到后，查路由服务拿 B 当前在哪台网关机。
- 如果 B 和 A 在同一台机器：内存直接投递。
- 如果不在：通过内部 RPC/MQ 把消息转发到 B 的网关机，再由那台机器的 WebSocket 推给 B。
- 投递成功后 A 网关机收到 B 的 ack，A 侧 UI 才能把消息标成「已送达」。

### 4.3 不丢不重
- 每条消息客户端生成一个 `client_msg_id`（UUID）。
- 服务端按 `client_msg_id` 去重：重发同一条不会重复存储。
- 服务端给每条消息分配全局递增 `seq_id`（按会话维度），客户端靠 seq 判断顺序和补拉缺失。
- 客户端发消息后没收到 ack，就按 client_msg_id 重试，服务端幂等。

### 4.4 离线消息
- B 不在线：消息写离线存储（按 `conversation_id` 分片），不丢。
- B 上线时：拉自己所有会话从 `last_ack_seq` 之后的消息。
- 拉完 ack，服务端清理已 ack 的离线消息（保留 N 天供多端同步）。

### 4.5 群聊
- 群消息扇出是大问题：一个 500 人群发一条消息，要推给 500 人。
- 写扩散（每条消息存一份到每个成员收件箱）：适合小群。
- 读扩散（群消息只存一份，成员上线自己拉）：适合大群。
- 实务：<100 人群写扩散，>100 人群读扩散。

## 五、权衡

| 选择 | 放弃了什么 | 为什么 |
|------|-----------|--------|
| WebSocket 长连接 | 连接管理复杂 | 实时推送必须长连接 |
| 一致性哈希固定连接 | 节点扩缩容有连接迁移 | 避免每台网关机维护全局用户表 |
| 消息按会话分片存储 | 跨会话查询难 | 聊天本来就是按会话访问 |
| 群聊小群写扩散 | 大群不能这么搞 | 小群体验好，大群单独优化 |

## 六、常见追问点

- **Q：消息会不会重复？**
  A：client_msg_id 幂等 + 服务端去重表，重试安全。
- **Q：群成员上万怎么搞？**
  A：走读扩散，群消息只存一份，成员上线按群 ID 拉；不能写扩散。
- **Q：多端同步？**
  A：每个设备维护自己的 ack 点，服务端按设备维度记录；同一账号多端都能收到。
- **Q：消息撤回怎么做？**
  A：发一条「撤回」系统消息带原消息 ID，客户端收到后把对应消息替换成「对方撤回了一条消息」。
- **Q：已读回执要不要可靠？**
  A：不需要强可靠，已读回执丢了用户也能忍；用 UDP 风格的尽力推送即可。
