# 04 · 案例：网页爬虫系统

> 考察重点：URL 去重、抓取调度、 politeness（礼貌抓取）、分布式队列、存储。

---

## 一、需求

**功能需求**
- 从一批种子 URL 开始，自动抓取网页内容。
- 解析页面中的链接，加入待抓取队列（广度优先爬取）。
- 提取正文、标题、发布时间等结构化数据。
- 支持对同一站点周期性重抓（更新检测）。
- 支持 URL 去重，不要重复抓同一页。

**非功能需求**
- 日抓取量亿级。
- 不能对目标站点造成压力（遵守 robots.txt、限速）。
- 去重要准（同一 URL 不同参数可能指向同一页）。
- 抓取和解析分离，方便水平扩展。

---

## 二、规模估算

- 日抓取 1 亿页面。
- 平均页面大小 500KB（含 HTML+资源，实际只存正文约 50KB）。
- 日原始下载流量 = 1 亿 × 500KB ≈ 50 TB/天。
- 正文存储 = 1 亿 × 50KB ≈ 5 TB/天，压缩后约 1-2 TB。
- 平均抓取 QPS = 1 亿 / 86400 ≈ 1160；峰值按 5 倍 ≈ 6000。

结论：IO 密集型，瓶颈在网络出口和目标站点 politeness。

---

## 三、高层设计

```
                ┌──────────────┐
                │  种子 URL 库  │
                └──────┬───────┘
                       ↓
              ┌────────────────┐
              │  调度中心 (Master)│
              └───┬────────┬────┘
                  ↓        ↓
         ┌──────────┐  ┌──────────┐
         │ Worker 1 │  │ Worker 2 │  ... 数十个抓取节点
         └────┬─────┘  └────┬─────┘
              ↓              ↓
        下载网页 → 解析 HTML → 抽正文 → 抽链接
                                  ↓
                          ┌───────────────┐
                          │ URL 去重队列   │（布隆过滤器 + Kafka）
                          └───────┬───────┘
                                  ↓
                          回收到调度中心
                                  ↓
                          存储：原始页 → S3/HDFS
                          结构化正文 → MySQL/ES
```

**核心组件**
- **Master 调度中心**：维护待抓取 URL 队列，按域名分组分配给 Worker。
- **Worker**：无状态抓取节点，真正发 HTTP 请求、解析页面。
- **URL 仓库**：存储已见 URL 集合，负责去重。
- **存储层**：原始 HTML 落对象存储，提取后的结构化数据进 ES 供搜索。

---

## 四、核心组件细节

### 4.1 URL 去重
- 用**布隆过滤器**在内存层快速判断「这个 URL 见过没」。亿级 URL 用几 GB 内存就能装下，误判率 1% 左右。
- 布隆过滤器说没见过的，再去 Redis/DB 精确查一次。
- URL 规范化：去掉 fragment（#）、去掉 UTM 参数、统一尾斜杠、转小写 host，再算哈希。否则 `a.com/page?utm_source=x` 和 `a.com/page` 会被当成两个页面。

### 4.2 抓取调度
- 按域名分组：同一个 site 的 URL 分给同一组 Worker，方便做站点级限速。
-  politeness：对同一域名每秒最多 N 个请求（可配），遵守 `Crawl-Delay`。
- 优先级：新闻门户优先级高于个人博客，重要站点先抓。
- 失败重试：5xx 或超时指数退避重试 3 次，4xx 直接放弃。

### 4.3 下载与解析
- Worker 用异步 HTTP 客户端（aiohttp/Scrapy）并发抓同域多个 URL。
- 解析用正则 + Readability 类库抽正文，比通用 HTML 解析稳。
- 抽出来的新链接过规范化 → 布隆过滤器 → Kafka 回 Master。

### 4.4 存储
- 原始 HTML 压缩后写对象存储（S3/OSS），key 用 URL 哈希，方便回溯。
- 结构化字段（title、正文、publish_time、url）写 ES，支持后续搜索。
- 抓取状态队列用 Kafka，削峰解耦。

### 4.5 周期性重抓
- 每抓一页记录 `last_crawled_at`。
- 定时任务按站点重要性分级：新闻站 5 分钟重抓一次，博客 24 小时，政府站一周。
- 比对内容哈希，没变就不更新索引，变了才写 ES。

## 五、权衡

| 选择 | 放弃了什么 | 为什么 |
|------|-----------|--------|
| 布隆过滤器去重 | 极小概率漏判新 URL | 内存命中率比全量查表快几个数量级 |
| 按域名分组调度 | Master 复杂 | 不分组会把小站点打挂 |
| 原始页存对象存储 | 不直接可查 | 主要靠 ES 查结构化数据，原始页留作回溯 |
| 异步重抓 | 数据不是最新 | 实时性要求不高，换吞吐 |

## 六、常见追问点

- **Q：爬虫会不会把目标站搞挂？**
  A：按域名限速 + robots.txt 遵守 + 错峰。我们是合作抓取时会直接和站点谈配额。
- **Q：布隆过滤器误判怎么办？**
  A：误判是把「新 URL」错判成「见过」，导致漏抓；误判率控制在 0.1% 以下可接受，重要站点走精确查。
- **Q：遇到登录墙/反爬怎么办？**
  A：登录态 Cookie 池 + 代理 IP 池 + 限速；强反爬站点放弃或和站点谈 API 合作。
- **Q：怎么处理海量 URL 队列？**
  A：Kafka 做缓冲，按域名分 partition，消费者水平扩展。
- **Q：和搜索引擎爬虫有什么区别？**
  A：搜索引擎是超大规模全量爬，我们是定向抓某些垂直领域，更看重内容质量和更新时效。
