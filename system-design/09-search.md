# 09 · 案例：搜索系统（倒排索引）

> 考察重点：倒排索引原理、写入链路、查询链路、相关性、分布式分片。

---

## 一、需求

**功能需求**
- 用户输入关键词，返回相关文档列表。
- 支持标题、正文、作者等多字段匹配。
- 支持分页、排序（按相关度/时间）。
- 支持搜索建议（输入时下拉提示）。

**非功能需求**
- 搜索 P99 < 300ms。
- 新文档 5 分钟内可被搜到（近实时）。
- 索引支持亿级文档。
- 高可用，单节点挂了不影响搜索。

---

## 二、规模估算

- 文档总量 10 亿篇。
- 平均文档大小 1KB。
- 搜索 QPS 峰值 1 万。
- 文档更新 QPS 1 万（新内容 + 修改）。

---

## 三、高层设计

```
  写入链路：
  业务库 (MySQL) → Binlog →  同步服务  →  构建倒排索引 →  ES 集群
                                                          ↓
  查询链路：                                              ┌────┐
  User → LB → 搜索服务 → ES 协调节点 → 广播到所有分片   → │ ES │
                                  ↓                       └────┘
                          合并结果、排序、取 Top N
                                  ↓
                          返回给用户
```

---

## 四、核心组件细节

### 4.1 倒排索引原理
- 正排索引：doc_id → 文档内容。我们熟悉的 DB 就是正排。
- 倒排索引：term（词）→ 包含这个词的 doc_id 列表。
- 搜索「苹果 手机」：
  - 查「苹果」倒排表 → [doc1, doc5, doc9]
  - 查「手机」倒排表 → [doc1, doc3, doc9]
  - 取交集 → [doc1, doc9]
  - 按相关度评分排序返回。
- 分词：中文要用 IK 之类分词器把「苹果手机」切成「苹果」「手机」。

### 4.2 写入链路
- 业务数据在 MySQL，搜索不能直接查 MySQL。
- Canal 订阅 MySQL binlog → 变更消息进 MQ。
- 索引服务消费 MQ，更新 ES 索引。
- ES 是近实时：写入后默认 1 秒（refresh_interval）才能被搜到，可接受。

### 4.3 查询链路
- 用户输入 `q=苹果手机`。
- 搜索服务调 ES：`bool -> must: match title "苹果手机", match body "苹果手机"`。
- ES 协调节点把请求广播到所有分片。
- 每个分片本地查倒排索引，返回 Top 100 候选。
- 协调节点合并所有分片结果，全局排序取 Top 20。
- 再批量取这些 doc_id 的正文摘要返回。

### 4.4 相关性
- 默认 BM25 算法：词频高、文档短、稀有词权重高。
- 业务要调：标题命中 > 正文命中；新文档加权；权威源加权。
- 用 ES 的 boost 字段或 function_score 自定义。

### 4.5 分片和扩展
- ES 索引按 hash 分成 N 个 shard，分布在多台节点。
- 读扩展：加副本（replica），查询负载分摊。
- 写扩展：加主分片，但分片数建索引时定好不能改（要 reindex）。
- 亿级文档一般 50 个主分片 + 1-2 副本。

### 4.6 搜索建议
- 用户输入过程中下拉提示。
- 用 ES 的 completion suggester 或单独维护一个热门词 Redis ZSET。
- 热门词按搜索频次排序，每天更新。

## 五、权衡

| 选择 | 放弃了什么 | 为什么 |
|------|-----------|--------|
| ES 而不是 MySQL like | 引入新系统 | like '%xx%' 全表扫不能用 |
| 近实时（1 秒） | 不是写入即见 | 搜索本来就容忍秒级延迟 |
| 按业务时间分索引 | 跨时间查询麻烦 | 老索引可以归档冻结 |
| Binlog 同步 | 多一跳 | 业务库和搜索引擎解耦 |

## 六、常见追问点

- **Q：ES 集群挂了一个节点？**
  A：有副本，其他节点继续服务；分片自动重分配。
- **Q：查询慢怎么优化？**
  A：加缓存（热门 query 结果 Redis）、过滤掉无效字段、用 filter context 不评分、加副本分摊查询。
- **Q：怎么处理同义词？**
  A：同义词词典在索引时扩展，「番茄」索引时同时加「西红柿」。
- **Q：搜索结果要不要做个性化？**
  A：基础搜索是全局排序，个性化是在基础结果上用用户画像重排（第二阶段）。
- **Q：索引重建怎么办？**
  A：建一个新索引，把老数据 reindex 过去，切流量到新索引，老索引下线；零停机。
