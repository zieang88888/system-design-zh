# 08 · 案例：电商购物车

> 考察重点：会话/登录态、读写比、并发更新、临时商品存储。

---

## 一、需求

**功能需求**
- 未登录用户也能加购物车（存在本地/浏览器）。
- 登录后多端同步购物车。
- 商品数量增减、删除、选中结算。
- 商品价格、库存实时展示。
- 下单后购物车清空。

**非功能需求**
- 购物车读多写少，但每个用户购物车数据量小。
- 不需要强一致（购物车不是钱，少一两个商品能忍）。
- 登录合并未登录购物车要顺滑。

---

## 二、规模估算

- DAU 1 亿，其中 30% 有购物车数据。
- 每个购物车平均 10 个商品。
- 读 QPS（打开购物车页）= 1 亿 × 10% / 86400 ≈ 1200，峰值 5 倍 ≈ 6000。
- 写 QPS（加购/改数量）≈ 读的 1/5 ≈ 1200 峰值。
- 单条购物车记录 200 字节，总数据量 = 3000 万 × 10 × 200B ≈ 60GB，Redis 轻松装下。

---

## 三、高层设计

```
  Client
    │
    ↓
  未登录：购物车存 localStorage / 本地 IndexedDB
    │
    ↓ 用户登录
  合并：本地购物车 → 上传到服务端 → 和服务端已有购物车合并
    ↓
┌──────────┐
│ 购物车服务 │
└─────┬────┘
      ↓
  Redis (HASH: cart:{userId} → skuId: {count, selected, added_at})
      ↓
  异步持久化：MySQL 作为冷数据备份/历史
      ↓
  结算时：购物车服务 → 查商品中心拿最新价格/库存 → 算金额
```

---

## 四、核心组件细节

### 4.1 存储选择
- **热数据全在 Redis**：HASH 结构，key = `cart:{userId}`，field = `skuId`，value = JSON `{count, selected, added_at}`。
- 为什么不直接 MySQL？购物车读太频繁，MySQL 扛不住；而且单用户数据小，Redis 存几亿购物车没压力。
- MySQL 做持久化兜底：Redis 异步刷盘或定期 dump，万一 Redis 丢了能从 MySQL 恢复。

### 4.2 登录合并
- 未登录时购物车在浏览器本地。
- 用户登录后，前端把本地购物车上传。
- 服务端合并逻辑：
  - 服务端已有该 sku：数量相加或以后端为准（产品策略）。
  - 本地有服务端无：直接加入。
- 合并后清空本地购物车。

### 4.3 价格和库存
- 购物车里**不存价格**（价格会变）。
- 用户打开购物车时，批量查商品中心拿最新价格、促销价、库存状态。
- 库存不足的商品置灰提示，不影响其他商品结算。
- 结算时再做一次最终价格校验和库存锁定，防止用户放购物车时便宜、结算时涨价。

### 4.4 选中结算
- HASH field 里带 `selected` 字段。
- 「全选/全不选」就是批量改这个字段。
- 结算只拉 `selected=true` 的条目。

### 4.5 下单后清空
- 支付成功后，MQ 通知购物车服务：把已下单的 sku 从购物车删除。
- 不是清空整个购物车，只删已结算的条目（部分结算场景）。

---

## 五、权衡

| 选择 | 放弃了什么 | 为什么 |
|------|-----------|--------|
| Redis 热存 | 数据可能丢 | 购物车丢了用户能接受，重加一次就行 |
| 不存价格 | 每次要查商品中心 | 价格变动频繁，存了会过期 |
| 未登录存本地 | 换设备购物车没了 | 登录后合并，体验可接受 |
| 异步刷 MySQL | 短暂不一致 | 购物车一致性要求低 |

## 六、常见追问点

- **Q：购物车数据要不要永久保留？**
  A：长期不活跃用户的购物车可以定期清理（比如 180 天没登录），减少存储。
- **Q：两个客户端同时加购同一个 sku？**
  A：Redis HSET 是单条原子操作，数量覆盖或累加看产品定义；用 Lua 脚本保证「读-改-写」原子。
- **Q：超卖怎么防？**
  A：购物车不扣库存，结算时才扣；购物车阶段只是「意向」。
- **Q：购物车里商品下架了？**
  A：打开购物车时商品中心返回「已下架」状态，前端置灰，不能结算。
- **Q：购物车要不要做推荐？**
  A：那是推荐系统的事，购物车页可以在旁边加「猜你想买」，不影响主流程。
