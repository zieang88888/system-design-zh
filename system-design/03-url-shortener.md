# 03 · 案例：URL 短链系统

> 经典入门题。考察重点：哈希/发号、缓存、读写比极大、跳转延迟。

---

## 一、需求

**功能需求**
- 输入一个长 URL，生成一个固定长度（约 6-8 字符）的短 URL。
- 用户访问短 URL 时 302 跳转到原长 URL。
- 支持自定义短码（可选）。
- 记录每次点击的基础统计（次数、地域、时间）。

**非功能需求**
- 跳转延迟 P99 < 100ms（用户体验关键）。
- 可用性 99.99%（短链挂了等于所有外链断了）。
- 读远多于写，预估读写比 100:1。
- 短码不能被暴力猜到（防爬敏感链接）。

**范围排除**：本期不做短链过期删除后台、不做团队协作、不做广告拦截。

---

## 二、规模估算

假设：
- 日新增短链 1000 万条。
- 日点击量 1 亿次。
- 平均长 URL 长度 500 字节，加上元数据每条约 600 字节。

计算：
- 写 QPS = 10,000,000 / 86400 ≈ 116。
- 读 QPS = 100,000,000 / 86400 ≈ 1157；峰值按 20 倍 ≈ 2.3 万 QPS。
- 年存储 = 1000 万 × 600 字节 × 365 ≈ 219 GB。
- 点击日志另算：1 亿条/天 × 100 字节 ≈ 10 GB/天，适合异步进数据仓库。

结论：写很轻，读很重，缓存是核心。

## 三、高层设计

```
                ┌─────────────┐
   用户浏览器 → │  CDN / 边缘  │
                └──────┬──────┘
                       ↓
                ┌─────────────┐      ┌──────────┐
                │   负载均衡   │ →   │ App 无状态│
                └─────────────┘      └────┬─────┘
                                          │
                          ┌───────────────┼───────────────┐
                          ↓                               ↓
                    ┌──────────┐                   ┌──────────┐
                    │  Redis 缓存│                   │  MySQL   │
                    └──────────┘                   └────┬─────┘
                                                         ↓
                                                  ┌──────────┐
                                                  │   MQ     │ → 点击统计服务 → 数仓
                                                  └──────────┘
```

**API**
```
POST /api/v1/links        body: { long_url, custom_alias? }  → { short_code }
GET  /{short_code}        302 redirect
GET  /api/v1/links/{code}/stats  → { clicks, by_country }
```

**数据模型**
```sql
TABLE short_links (
  id           BIGINT PRIMARY KEY,
  short_code   VARCHAR(10) UNIQUE NOT NULL,
  long_url     VARCHAR(2048) NOT NULL,
  user_id      BIGINT,
  created_at   DATETIME,
  expire_at    DATETIME,
  INDEX idx_code (short_code)
);

TABLE click_events (
  id          BIGINT PRIMARY KEY,
  short_code  VARCHAR(10),
  ip          VARCHAR(45),
  country     VARCHAR(2),
  ua          VARCHAR(255),
  ts          DATETIME,
  INDEX idx_code_ts (short_code, ts)
);
```

## 四、核心组件细节

### 4.1 短码生成
两种主流方案，我选**发号器 + base62 编码**：
- 全局发号器（雪花 ID 或号段）发一个递增的 64 位数字 ID。
- 把这个数字转成 base62（0-9a-zA-Z，共 62 字符），前 7 位就是短码。
- 优点：天然无碰撞、趋势递增、不需要查库试错。
- 备选：long_url 取 MD5 前 6 位，碰撞概率不为零，要靠唯一索引兜底重试。

为什么不用自增 ID 直接拼？因为自增 ID 可被枚举，别人可以遍历你的短链。发号器+base62 后虽然仍然可枚举，但加一层随机化偏移就破解了。

### 4.2 读路径（跳转）
1. 用户访问 `https://s.io/abc123`。
2. CDN 边缘节点：如果短链设了强缓存，直接 301 不需要回源；但短链跳转我们一般用 302，因为可能要统计点击或临时下线，所以 CDN 只缓存静态资源不缓存跳转。
3. 请求到 LB → App。
4. App 先查 Redis：`GET link:abc123`，命中直接取 long_url 返回 302。
5. 未命中查 MySQL，查到后写回 Redis（TTL 1 小时），返回 302。
6. 异步发一条点击事件到 MQ，不阻塞跳转响应。

为什么用 302 而不是 301？301 是永久重定向，浏览器会强缓存，我们就失去了后续统计和改跳转的能力；302 每次都经过我们服务器。

### 4.3 写路径（创建）
1. 用户提交 long_url。
2. App 调发号器拿一个全局 ID。
3. base62 编码成短码。
4. 插入 MySQL（short_code 有唯一索引兜底）。
5. 预热写 Redis。
6. 返回短码给用户。

### 4.4 点击统计
- 每次跳转不直接写 DB，而是发 MQ 消息。
- 统计服务消费 MQ，批量（每 1000 条或每秒）写 ClickHouse / 数仓。
- 实时接口（最近 1 小时点击数）用 Redis 计数器 `HINCRBY` 近似。

## 五、权衡

| 选择 | 放弃了什么 | 为什么这么选 |
|------|-----------|-------------|
| 发号器 + base62 | 需要中心化发号服务 | 避免哈希碰撞重试，写入路径稳定 |
| 302 而非 301 | 每次都要回源，成本高 | 保留统计和临时下线能力 |
| Redis 做缓存 | 引入一致性窗口 | 读 QPS 2 万级，DB 扛不住 |
| 异步统计 | 统计秒级延迟 | 不阻塞跳转主链路 |
| 单库 MySQL | 未来要分库 | 现在写 QPS 仅 116，单库够 |

## 六、常见追问点

- **Q：短码被暴力枚举怎么办？**
  A：短码从 6 位升到 7-8 位（62^8 ≈ 218 万亿），枚举成本指数上升；敏感链接加访问密码或时效。
- **Q：发号器挂了？**
  A：发号器多实例部署，每个实例号段不重叠（比如实例 A 用奇数段、B 用偶数段），挂一个另一个继续发。
- **Q：Redis 缓存被击穿？**
  A：热点短链（比如明星微博的短链）用本地缓存 + 互斥锁回填；TTL 加随机抖动防雪崩。
- **Q：用户提交了恶意 URL？**
  A：创建时做 URL 安全校验（接第三方安全 API），维护黑名单。
- **Q：短链要过期怎么办？**
  A：expire_at 字段 + 定时任务扫表清理；跳转时判断过期就返回 410。
