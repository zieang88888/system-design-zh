# 13 · 规模估算速查：面试里张口就来的数字

> 系统设计面试里，面试官经常让你估算 QPS、存储、机器数。本篇把常用数量级背下来，面试时不用拿计算器。

---

## 一、换算基础

```
1 秒 = 1000 ms
1 分钟 = 60 秒 = 60,000 ms
1 小时 = 3600 秒
1 天 = 86,400 秒 ≈ 10^5 秒（粗算用 10 万秒）
1 年 ≈ 3 × 10^7 秒

1 KB = 1024 B ≈ 10^3 B（粗算用 1000）
1 MB ≈ 10^6 B
1 GB ≈ 10^9 B
1 TB ≈ 10^12 B
1 PB ≈ 10^15 B

带宽单位：1 Gbps = 1000 Mbps ≈ 125 MB/s
```

---

## 二、QPS 估算套路

### 公式
```
平均 QPS = DAU × 人均请求数 / 86400
峰值 QPS ≈ 平均 QPS × 10~100（看业务类型）
```

### 常见场景的经验值
| 场景 | 平均 QPS | 峰值 QPS |
|------|----------|----------|
| 小型 App（DAU 10 万） | 几百 | 几千 |
| 中型业务（DAU 1000 万） | 几千 | 几万 |
| 大型社交（DAU 1 亿） | 几万 | 几十万 |
| 超级 App（微信级） | 几十万 | 百万级 |

### 峰值倍数怎么估
- 纯读（刷 Feed、刷商品）：峰值 ≈ 平均的 10-20 倍。
- 秒杀/抢购：峰值 ≈ 平均的 100-1000 倍，必须靠 MQ 削峰。
- 办公/企业类：白天工作时间集中，峰值 5-10 倍。

---

## 三、单机性能量级

> 这些数字面试时直接说「经验值」，不用精确。

| 组件 | 量级 | 说明 |
|------|------|------|
| 单机 MySQL 点读 QPS | 5,000 ~ 15,000 | 简单主键查询，带缓存前提 |
| 单机 MySQL 写 TPS | 1,000 ~ 5,000 | 看行锁竞争和事务大小 |
| 单机 MySQL 单表行数 | 千万级 | 到亿级就要考虑分表 |
| Redis 单实例 QPS | 10 万 ~ 100 万 | 纯内存、单线程、简单 get/set |
| Redis 单实例内存 | 10-50 GB | 再大就要分片 |
| Nginx 静态文件 QPS | 3 万 ~ 5 万 | 主要瓶颈在带宽 |
| 应用服务器 Tomcat/QPS | 500 ~ 2000 | 看业务逻辑复杂度 |
| Kafka 单集群写入 | 百万条/秒 | 批量+顺序写 |
| ES 单节点查询 QPS | 几百 ~ 几千 | 看查询复杂度 |
| 单机带宽 | 1 Gbps ≈ 125 MB/s | 网卡上限 |

## 四、存储估算

### 公式
```
年存储 = 日新增行数 × 单行大小 × 365
```

### 常见单条记录大小
- 短链映射：~200 字节
- 用户资料：~1 KB
- 一篇文章：~5-50 KB
- 一条聊天消息：~500 字节
- 一条日志：~200 字节
- 一张缩略图：~50 KB

### 例子
「日增 100 万条聊天记录，每条 500 字节，年存储 = 100 万 × 500 × 365 ≈ 182 GB」——单机 MySQL 单库一年就到 200GB 数据，要开始考虑分库或归档。

---

## 五、带宽估算

```
出口带宽 (MB/s) = QPS × 平均响应大小 (KB) / 1024
```

### 例子
「读 QPS 3 万，每页返回 20KB，出口带宽 = 3 万 × 20KB / 1024 ≈ 586 MB/s ≈ 4.7 Gbps」——单机房 10G 网卡能扛，但要 CDN 卸载大部分静态流量。

---

## 六、缓存命中率经验

| 命中率 | 实际效果 |
|--------|----------|
| 95% | DB 压力只剩 5%，基本高枕无忧 |
| 90% | DB 还有 10% 流量，可接受 |
| 80% | DB 压力不小，要优化热点 key |
| < 80% | 缓存基本白加，查缓存成本都比直接查 DB 高了 |

**CDN 命中率**：静态资源 95%+ 正常；动态接口不应走 CDN。

## 七、其他常用数字

- **一次数据库事务**：1-10 ms（本地磁盘）。
- **一次 Redis 读**：0.1-1 ms。
- **一次同机房 RPC**：1-5 ms。
- **一次跨机房 RPC**：20-100 ms（看机房距离）。
- **一次 HTTPS 握手**：50-200 ms（含网络 RTT）。
- **人类感知卡顿阈值**：100 ms（以内觉得即时），1 秒（内觉得流畅），10 秒（内必须有反馈）。
- **SLA 几个 9 的年宕机时间**：
  - 99%：3.65 天
  - 99.9%：8.76 小时
  - 99.99%：52.6 分钟
  - 99.999%：5.26 分钟

## 八、估算练习（自己算一遍）

1. **设计 Twitter 级 Timeline**：DAU 3 亿，人均每天发 2 条、读 100 条。
   - 写 QPS = 3 亿 × 2 / 86400 ≈ 7000。
   - 读 QPS = 3 亿 × 100 / 86400 ≈ 35 万，峰值 10 倍 = 350 万。
   - 结论：读极重，必须推模式缓存。

2. **设计 Instagram 级图片存储**：日增 5000 万张图，平均 2MB。
   - 日存储 = 5000 万 × 2MB = 100 TB/天。
   - 年存储 ≈ 36 PB。
   - 结论：必须对象存储 + CDN，不能自己买磁盘。

3. **设计短链服务**：日新增 1000 万条。
   - 写 QPS ≈ 116。
   - 读 QPS 假设读写比 100:1 ≈ 1.2 万，峰值 10 倍 = 12 万。
   - 结论：写很轻，读靠 Redis 扛。

---

## 九、面试估算心法

1. **先给假设**：DAU 多少、人均多少、读写比多少。
2. **粗算即可**：用 10^5 代替 86400，用 1000 代替 1024。
3. **算完反推机器数**：QPS / 单机承载 = 需要的节点数，再 ×2 冗余。
4. **别纠结精确**：面试官看的是你会估，不是你算得准。
