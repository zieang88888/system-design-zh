# 07 · 案例：在线支付系统

> 考察重点：强一致、幂等、对账、第三方回调、状态机。

---

## 一、需求

**功能需求**
- 用户下单后发起支付，调起微信/支付宝。
- 第三方支付渠道异步回调通知结果。
- 支付成功后通知业务方发货/开通权益。
- 支持退款。
- 对账：每天和渠道对一次账。

**非功能需求**
- 绝对不能出现「钱扣了但订单没成功」或「订单成功了钱没扣」。
- 一致性要求最高（钱的问题）。
- 可用性 99.999%（资金链路不能挂）。
- 所有操作可审计、可追溯。

---

## 二、规模估算

- 日订单 100 万，支付成功率 95%。
- 支付 QPS ≈ 100 万 / 86400 ≈ 12；峰值秒杀 1000 QPS。
- 回调 QPS 和支付差不多。
- 存储量小（日增 100 万行 × 1KB ≈ 1GB/天），但必须强一致。

结论：流量不大，但一致性和正确性要求极高，重点不在扩展而在可靠。

---

## 三、高层设计

```
  App/小程序
    ↓ 下单
┌──────────┐   同步    ┌──────────────┐
│ 订单服务 │ ───────→ │  支付网关服务  │
└────┬─────┘          └──────┬───────┘
     │                       ↓
     │                调微信/支付宝 SDK
     │                       ↓
     │                用户在第三方完成支付
     │                       ↓
     │                第三方异步回调（可能多次、乱序、重复）
     │                       ↓
     │                ┌──────────────┐
     └──────────────→ │  支付状态机   │  幂等更新
                      └──────┬───────┘
                             ↓
                       发 MQ 通知订单服务
                             ↓
                       订单状态变「已支付」→ 发货
                             ↓
                       对账系统 T+1 跑批，和渠道账单核对
```

---

## 四、核心组件细节

### 4.1 支付状态机
一笔订单的状态只能是：
```
待支付 → 支付中 → 支付成功
                → 支付失败
                → 已退款
```
- 每次状态更新都带前置状态条件，比如只有「支付中」才能变「支付成功」。
- 用数据库乐观锁：`UPDATE orders SET status='PAID' WHERE id=? AND status='PAYING'`，影响行数=0 说明已经被处理过，直接返回成功。

### 4.2 幂等
- 每笔支付请求生成全局唯一 `payment_no`，传给第三方。
- 第三方回调时带这个 `payment_no`，服务端用它做幂等键。
- 回调进来先查支付单：已经是「支付成功」就直接返回 success，不重复处理。
- 前端重复点「支付」按钮也安全：同一 `order_no` 只能有一个有效支付单。

### 4.3 回调可靠性
- 第三方回调可能：丢、重复、乱序、延迟。
- 我们的应对：
  - 回调接口幂等（上面那条）。
  - 处理完才返回 success；处理中先返回 500，第三方会重试。
  - 除了被动等回调，我们**主动查单**：支付发起后 5 秒、30 秒、2 分钟定时任务主动问第三方这笔单状态，兜底回调丢失。

### 4.4 通知业务方
- 支付成功后不能直接同步调订单服务（耦合、可能对方挂）。
- 发 MQ 消息 `payment_success`，订单服务消费。
- 消费端同样幂等（按 order_no）。
- 消费失败重试，死信队列人工介入。

### 4.5 退款
- 退款也是状态机：`已支付 → 退款中 → 退款成功 / 退款失败`。
- 退款要走第三方退款 API，同样有异步回调。
- 部分退款要记录已退金额，不能超过原支付金额。

### 4.6 对账
- T+1 凌晨下载渠道账单文件。
- 逐笔和本地支付单比对：
  - 本地有、渠道无：我们说付了但渠道没收到，可疑，人工介入。
  - 渠道有、本地无：渠道扣了钱但我们没记录，补单。
  - 两边金额不一致：告警。
- 对账差异自动生成工单，财务人工处理。

## 五、权衡

| 选择 | 放弃了什么 | 为什么 |
|------|-----------|--------|
| 强一致状态机 | 性能开销 | 钱不能错 |
| 回调被动+主动查单双保险 | 多一轮查询 | 防止回调丢单 |
| MQ 异步通知业务方 | 秒级延迟 | 解耦支付和订单，互不影响可用性 |
| 对账 T+1 | 不是实时 | 资金对账本来就日终做 |

## 六、常见追问点

- **Q：用户支付成功但回调没收到，订单还是待支付？**
  A：主动查单兜底，定时任务问渠道；最终一致。
- **Q：回调重复发了两次？**
  A：幂等，第二次直接返回 success，不重复通知业务方。
- **Q：分布式事务要不要用？**
  A：支付和订单之间不用 XA 强事务，用本地消息表 + MQ 最终一致；钱和渠道那一边靠状态机+对账保证。
- **Q：怎么防止重复退款？**
  A：退款单号唯一索引 + 状态机只能退一次 + 已退金额累加校验。
- **Q：渠道宕机了？**
  A：支付网关层做多渠道路由，微信挂了切支付宝；都挂了就支付页提示稍后重试，不能让用户钱扣了没反应。
